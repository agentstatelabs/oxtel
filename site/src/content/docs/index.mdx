The first line is oxtel's own. It says, in plain words, where each kind of telemetry goes, and here that nothing leaves the program. After it come the program's lines. Each field is a key of its own, and lines inside a span carry its fields and its trace id, so you can find everything one request did. CI runs the example and checks it still prints these lines.

## Three steps, no rewrites

<Steps>

1. **Logs.** `oxtel::init()`, as above. Text on a terminal, JSON anywhere else, and `RUST_LOG` chooses how much.

2. **Requests.** For a web service, one layer on an axum router gives every request a span, a log line and duration metrics:

   <Example file="examples/web.rs" region="serve" />

3. **Send it somewhere.** Point oxtel at an OpenTelemetry Collector or any backend that takes OTLP. The code doesn't change:

   ```bash
   OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 OTEL_SERVICE_NAME=shop cargo run
   ```

</Steps>

[Get started](/start/) goes through each step.

## Why oxtel

<CardGrid>
	<Card title="Your code doesn't change" icon="seti:rust">
		Rust code already records spans, logs and metrics with `tracing` and `metrics`. oxtel turns them into log lines, OTLP for collectors and backends, and Prometheus scrapes. There's no second API to learn, and no bridge between two.
	</Card>
	<Card title="One line per framework" icon="puzzle">
		A layer for axum and tower services, a wrapper for MCP servers and clients, one line for SQLite, PostgreSQL and sqlx. Each records what the OpenTelemetry conventions name, under their names.
	</Card>
	<Card title="Nothing is sent until you say so" icon="approve-check">
		With no settings, you get log lines and nothing else. Set `OTEL_EXPORTER_OTLP_ENDPOINT` and traces, metrics and logs go there, with no rebuild. A program that only wants logs can leave out every HTTP and TLS crate.
	</Card>
	<Card title="Failures are explained" icon="information">
		When sending fails, oxtel says so at once, with where it was sending, why it failed and what to check. Then it counts quietly, and says when sending works again.
	</Card>
</CardGrid>

## Faster than the official stack

Measured against the official OpenTelemetry Rust SDK with `tracing-opentelemetry`, doing the same work on the same machine, in October 2026. Lower is better.

| What | oxtel | Official stack |
|---|---|---|
| A span with 3 fields | **258 ns** | 671 ns |
| A span that isn't sampled | **84 ns** | 589 ns |
| A counter, with attributes on each call | **13 ns** | 23 ns |
| A counter, 8 threads on one series | **0.4–0.6 ns** | 20–65 ns |
| CPU per span, sent over OTLP at 40,000 spans/s | **5.3 µs** | 7.2 µs |

In a burst, oxtel exports 1.9 times as many spans a second, with 2.5 times less CPU per span, and both stay within 1.5 MiB. [The benchmarks](https://github.com/agentstatelabs/oxtel/blob/main/bench/RESULTS.md) say how each was measured and made fair, with every number and how to reproduce them.

## Checked against the real thing

- **An OpenTelemetry Collector** decodes oxtel's traces, metrics and logs on every change, over protobuf and JSON, and CI compares what it got with what was sent. [The conformance tests](https://github.com/agentstatelabs/oxtel/blob/main/conformance/README.md) list what's checked.
- **Prometheus's own checker**, `promtool`, reads oxtel's `/metrics` page, and the Collector's Prometheus receiver scrapes it.
- **The names come from the conventions.** OpenTelemetry's Weaver generates them from a pinned conventions release, and CI checks they match.
