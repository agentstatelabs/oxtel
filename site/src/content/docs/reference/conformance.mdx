## Prometheus's own tools

- **promtool**, Prometheus's own checker, parses and lints oxtel's classic text format.
- **A strict OpenMetrics parser,** from the Prometheus Python client, reads oxtel's OpenMetrics, which Prometheus asks for when it scrapes.
- **The Collector's Prometheus receiver** scrapes oxtel's `/metrics`, as above.
- **A Prometheus server** scrapes it, and takes metrics pushed over OTLP, on the [Prometheus page](/backends/prometheus/)'s stack.

## The configuration schema

The example configuration files, and the test fixtures taken from the OpenTelemetry configuration project's own examples, are validated against the JSON schema that project publishes, at the version CI pins. oxtel's tests then read those files and check what they set up.

## The semantic conventions

oxtel names what it records with the OpenTelemetry semantic conventions, and the names are generated, not typed:

- **oxtel-semconv** is generated by OpenTelemetry's Weaver from a pinned release of the conventions. CI generates it again, and must find nothing changed.
- **The instrumentation crates' tests** check each attribute and metric they record against those definitions: all but oxtel-tokio's, which the conventions don't define. The tests keep the names they recorded, from which [every span and metric](/reference/telemetry/) is generated.

## The site's own examples

The site is checked as code too:

- **Every example program** builds with exactly the dependencies its page shows, and those whose output a page shows print it still.
- **[Every backend's stack](/backends/)** receives what its page says it will, and **[every deployment](/deploy/docker/)** stops cleanly, as its platform stops it.
- **[Every setting](/reference/settings/)** the code reads is on its page, and every link between pages leads somewhere.
