## Where oxtel is slower or does less

In the numbers above:

- **A log event outside any span** costs about the same with both, and the official appender is a few percent faster. Inside a span, oxtel is faster.
- **Memory in a burst.** Both stay bounded, and oxtel's peak is a little higher than the official SDK's.
- **A histogram recorded from many threads at once.** oxtel's counters spread across threads when they contend; its histograms don't yet, so every thread updates the same atomics.
- **Exemplars cost something.** A measurement inside a sampled span is slower with exemplars on, which is oxtel's default. The official SDK doesn't record exemplars at all. `OTEL_METRICS_EXEMPLAR_FILTER=always_off` turns them off.

In what it does:

- **No OpenTelemetry API.** oxtel records what `tracing` and `metrics` record. Code instrumented with the `opentelemetry` crate's own API, a library's included, isn't recorded.
- **No instruments with callbacks.** The `metrics` crate has none, so a value read on demand, such as a queue's length, is set as a gauge when it changes, or by a thread of your own, [as oxtel-tokio does](/guide/libraries/#the-tokio-runtime-oxtel-tokio).
- **The standard samplers only:** always on, always off, a ratio of traces, and following the parent, chosen with `OTEL_TRACES_SAMPLER`. There's no way to write your own.
- **Fewer exporters:** OTLP over HTTP and gRPC, OTLP/JSON lines, Prometheus and the console. There's no Zipkin exporter.
- **Fewer span attributes** than tracing-opentelemetry records by default: no source location, thread, or busy and idle times.
- **Not yet:** detecting cloud providers, and remote management with OpAMP. [What works with what](/reference/integrations/) has the plans.
- **Younger.** oxtel is at 0.4, its API will change before 1.0, and it isn't part of the OpenTelemetry project.
