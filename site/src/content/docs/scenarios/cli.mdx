The whole run is one span, `primes`, so its lines carry the limit and the run's trace id. Given something that isn't a number, the tool logs the error inside the same span, at `error`, and exits with status 1. CI runs the example and checks it still prints these lines.

## Exiting without losing anything

Once oxtel sends telemetry somewhere, it sends traces and logs in batches, in the background, and metrics every 60 seconds. A tool that runs for a second would exit before any of that happened, if it weren't for the guard: the value `oxtel::init()` returns. Dropping it sends everything still pending, and waits for that to finish.

- **Return from `main`,** on failure too. Return an `ExitCode`, as here, or an error. Either way `main` ends normally and the guard is dropped. `std::process::exit` ends the process on the spot and drops nothing, so the last batch is lost. If you must call it, drop the guard first.
- **Create the guard first.** Rust drops a function's values in the reverse of the order they were made, so the guard, made first, is dropped last, after any span still open has ended and can be sent with the rest.
- **A panic** in `main` drops the guard as it unwinds, so what was pending is still sent. With `panic = "abort"` in the build profile, nothing is dropped.
- **An unreachable collector** delays exit by at most 5 seconds. `oxtel::builder().with_shutdown_timeout(...)` changes that.

## For production

- **Keep standard output for results.** `OXTEL_LOG_OUTPUT=stdout` would put log lines among them.
- **Name the tool.** Set `OTEL_SERVICE_NAME`; otherwise backends show `unknown_service:` and the executable's name.
- **Expect one trace per run.** With a span around the run, as here, a backend shows each run as one trace, with everything it logged.
